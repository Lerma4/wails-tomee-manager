## Project Overview

**tomee-manager** is a desktop application for managing a local Apache TomEE server. It allows users to configure TomEE paths/ports, manage WAR artifact deployments, and start/stop/restart the server with live log streaming. Built with [Wails v2](https://wails.io/) (Go backend + React/TypeScript frontend).

## Commands

### Development
```bash
wails dev          # Run in live development mode (starts both Go backend and Vite dev server)
```


## Architecture

### Backend (Go)

- **main.go** — Wails app entry point. Initializes services, binds them to the frontend, and embeds `frontend/dist` via `//go:embed`.
- **app.go** — `App` struct with Wails lifecycle (`startup`) and native dialog helpers (`SelectDirectory`, `SelectProjectDir`).
- **backend/service/storage.go** — `StorageService`: SQLite persistence (via `modernc.org/sqlite`, pure Go, no CGO). Database stored at `os.UserConfigDir()/tomee-manager/data.db`. Manages `config` (singleton row) and `wars` tables.
- **backend/service/tomee.go** — `TomEEService`: Start/Restart via `catalina.bat`/`catalina.sh`; Stop speaks Tomcat's shutdown protocol over a socket (see Key Patterns). Rewrites `server.xml` ports with the `etree` XML library. Streams parsed log records to the frontend via the `tomee-log` event and boot phases via `tomee-status` (`starting` / `running` / `stopped`).
- **backend/service/logparse.go** — Turns raw catalina output into `LogEntry{Level, Text}` records. This is where multi-line records and localised level names are handled; see Key Patterns.
- **backend/service/instance.go** — `CATALINA_BASE` resolution and the isolated-instance directory, plus context-descriptor helpers (`contextName`, `writeContextDescriptor`).
- **backend/service/war.go** — `WarService`: deploys, undeploys, and reports deployment state for WAR artifacts in three modes (see Key Patterns).
- **backend/model/config.go** — Data models: `Config` (paths, ports, VM options, flags) and `WarArtifact` (source path, dest name, enabled flag, deploy mode).

All services are bound to the frontend in `main.go` — their exported methods become callable from TypeScript via auto-generated bindings in `frontend/wailsjs/` (gitignored, regenerated by `wails dev`/`wails build`).

### Frontend (React + TypeScript)

- **Tech stack**: React 18, React Router (HashRouter), Tailwind CSS v4, DaisyUI v5, Vite
- **frontend/src/App.tsx** — Router with three routes: `/` (Dashboard), `/wars` (WAR Manager), `/config` (Configuration)
- **Pages**:
  - `Dashboard.tsx` — Start/Stop/Restart buttons + live log viewer (subscribes to `tomee-log` Wails event)
  - `WarManager.tsx` — CRUD table for WAR artifacts + "Deploy All" action
  - `Configuration.tsx` — Form for TomEE path and port settings
- **Go bindings** are imported from `../../wailsjs/go/service/` and `../../wailsjs/go/main/` (e.g., `Start()`, `LoadConfig()`, `DeployAll()`)

### Key Patterns

- **TomEEService concurrency**: Public methods (`Start`, `Stop`, `Restart`) acquire `s.mu`; internal `startLocked`/`stopLocked` assume caller holds the lock. A background goroutine clears `s.process` on natural exit.
- **Log levels are not where you would expect them**: TomEE 1.7 (Tomcat 7) uses `java.util.logging`'s `SimpleFormatter`, which splits one record over two lines and *localises the level name* — on an Italian JVM the levels read `GRAVE` / `AVVERTENZA` / `INFORMAZIONI`, and they sit on the line *after* the timestamp. On top of that, `ConsoleHandler` writes everything to **stderr**, so tagging by stream marks the entire log as errors. `logparse.go` groups each record (header + level line + stack trace) into one `LogEntry` and classifies it; do not go back to per-line, per-stream tagging.
- **Stopping does not use `shutdown.bat`**: the script spawns a JVM that resolves the default address `localhost` to `::1` on a dual-stack Windows host and connects with the single-address `Socket` constructor, while the server binds its shutdown socket on `127.0.0.1` — so it fails with "Could not contact localhost:8005". `sendShutdownCommand` writes the shutdown string to the port directly. Killing the process is only the fallback, and only for a server this app started.
- **Deploy modes** (`model.DeployCopy` / `DeployWar` / `DeployExploded`): `copy` puts the `.war` in `webapps/`; the other two write a context descriptor in `conf/Catalina/localhost/` pointing at the build output in `target/`, so nothing is copied and `exploded` picks up a rebuild in place. Only one form may exist at a time or Tomcat deploys the context twice — `deployment.clear` enforces that. On Windows a running Tomcat holds the descriptor open, so `writeContextDescriptor` skips writing when the contents would not change (this is what lets a re-deploy succeed while the server runs).
- **Isolated instance** (`Config.IsolatedBase`, off by default): runs against a private `CATALINA_BASE` seeded once from the installation's `conf/`, leaving `server.xml` and `webapps/` in the TomEE install untouched. `CATALINA_HOME` always stays the installation — the startup scripts live there.
- **Go → Frontend communication**: Wails `EventsEmit` for log streaming; frontend listens via `EventsOn` from `wailsjs/runtime/runtime`
- **Frontend → Go communication**: Direct function calls via Wails-generated TypeScript bindings (no REST API)
- **Single-row config**: The `config` table enforces `id = 1` via CHECK constraint
- **Cross-platform**: TomEE service selects `catalina.bat` vs `catalina.sh` based on `runtime.GOOS`

### Versioning

- **Source of truth**: `frontend/package.json` → campo `"version"` (es. `"0.1.0"`)
- **Build-time injection**: `vite.config.ts` espone `__APP_VERSION__` via `define` — usata dal componente `Footer.tsx`
- **Git tag convention**: i tag devono corrispondere alla versione in `package.json` (es. `v0.1.0`)
- Quando si rilascia una nuova versione: aggiornare `"version"` in `package.json` e taggare il commit (`git tag v<version>`)
